# 性能基线（检索链路）

评审遗留项「无性能基线」的交付物。此前只量过一处（网关客户端复用：410 → 268 ms/次），
剩下的"检索到底多快、慢在哪、能撑多大"完全靠感觉。这份文档 + `backend/scripts/bench.py`
把它变成**可重复跑、可对比**的数字。

## 怎么跑

```bash
cd backend && ../.venv/bin/python scripts/bench.py            # 打印表格
cd backend && ../.venv/bin/python scripts/bench.py --check    # 与入库基线比，超 1.5× 退出码 1
cd backend && ../.venv/bin/python scripts/bench.py --write    # 更新 docs/perf-baseline.json
```

脚本自建一个隔离库（默认 `umaxrag_bench`，可用 `BENCH_DB` 覆盖）并顺手用 Alembic 建表，
**全程假 embedder、不调模型**：不花 key、不依赖网络，所以任何机器上都能重复跑。
它量的是**我们能控制的那部分**——模型调用变慢不是我们的代码变慢，混进来只会让基线不可比。

## 实测（2026-10-08，MacBook arm64 / Python 3.14.7，best-of-3）

| 语料规模 | 端到端 | 取块（SQL→Python） | 分词+建 BM25 | 向量路（pgvector） |
|---:|---:|---:|---:|---:|
| 500 切块 | **44.6 ms** | 0.8 | 31.5（71%） | 6.6 |
| 2 000 | **153.7 ms** | 4.1 | 118.3（77%） | 15.0 |
| 8 000 | **580.0 ms** | 12.5 | 497.2（86%） | 34.9 |

- **入库**：21 KB 中文文本 → 30 个切块，**30.8 ms**（解析 + 切块 + 假向量 + 写库，不含模型 HTTP）。
- **并发**（8 线程 × 4 次，语料 2 000）：吞吐 **7.79 q/s**，p50 969 ms、p95 1 207 ms。
  单线程同一语料是 153.7 ms（≈6.5 q/s）——**8 线程只换来约 1.2× 吞吐**。

## 读出来的三件事

**① 检索是 O(语料) 的，而且常数很大。** 语料 ×4 → 延迟 ×3.5（44.6 → 153.7 → 580.0）。这不是"向量库慢"，而是每次查询都把全库切块重新处理了一遍。

**② 瓶颈在 Python 里，不在数据库。** 把"分词+建 BM25"再拆一层（2 120 块，jieba 词典已热身）：

| 步骤 | 耗时 | 说明 |
|---|---:|---|
| `jieba.cut_for_search` 全文重分词 | **139.8 ms**（94%） | `_bm25_ranking` 每次请求对**整个语料**重切一遍 |
| `BM25Okapi(corpus)` 建索引 | 7.3 ms | 同样每次重建 |
| `get_scores(query)` 打分 | 0.9 ms | **只有这一步天然与查询相关** |

也就是说：**一次 `/retrieve` 里约 70% 的时间花在"把已经处理过的内容再切一遍词"**，而那部分与查询无关、内容没变就该复用。向量路（pgvector 全表 `ORDER BY embedding <=> q`，`chunks.embedding` 上没有 ANN 索引）只占 ~6%，在 8 000 块时也才 35 ms——**当前规模下它不是瓶颈**。

**③ 加线程不解决，因为工作受 GIL 限制。** 8 并发吞吐仅 1.2×、单请求延迟从 154 ms 涨到 969 ms，是纯 Python 计算被串行化的典型指纹。结论：**单进程检索吞吐上限 ≈ 6–8 q/s**，靠加 uvicorn worker 进程线性扩展，靠加线程不行。

## 由此得到的两个结论（给决策用，本轮未实施）

**A. jieba 分词结果按内容缓存，是收益最大且语义安全的一步。**
`jieba.cut_for_search(text)` 是 `text` 的纯函数，用内容寻址的 LRU（`functools.lru_cache(maxsize=N)`，线程安全、有界）缓存切块的分词结果，**不需要任何失效逻辑**——内容变了 key 就变了。代价只有内存（每块几十个词的 token 列表）。按上表估算，2 000 块的重复查询可从 154 ms 降到约 25 ms 量级（省掉 118 ms 的分词，剩下取块 4 + 建索引 7 + 向量 15）。首次见到某块内容时仍是现在的速度。
**没有本轮就做**：它引入缓存（内存/上限/首查变慢这些参数），是有取舍的设计决定，且会改变基线口径（冷/热两套数字），该由你拍板；而且当前实测规模下 154 ms 的绝对延迟对私有化部署够用，不是必须先修。

**B. 真要撑更大语料，得动结构而不是调参数。**
现在三条路都是全量扫描（取块 `SELECT` 全库、BM25 在 Python 里建、向量在 PG 里全表算距离）。到十万块量级时：BM25 该换成 PG 全文检索（`tsvector` + GIN）或常驻索引，向量该加 HNSW/IVFFlat。**目前不需要**——按 ① 的曲线，8 000 块 ≈ 0.6 s，先到瓶颈的是"并发多用户"（③）而不是"语料大"。

## 诚实标注

- 数字是**本机**的，绝对值只在同一台机器上可横向比较；跨机器有意义的信号是**随语料规模的曲线与各项占比**。
- 语料是伪中文（固定种子），分词工作量真实但内容无意义；`hits` 恒为 5 说明召回链路是通的，但不评估**相关性**质量（那是 `eval` 那套的职责）。
- 打分口径是 best-of-3：本机噪声大，取最小值最能反映"代码本身有多快"；p95 一并存进 `docs/perf-baseline.json` 供参考。
- 首查会额外付一次 jieba 词典加载（约 0.3 s，之后走缓存文件）——脚本热身掉，所以不在表里。
- **没有接进 `scripts/run_gates.sh` / CI 主门禁**：共享 runner 上的耗时是噪声，误红比漏报更糟。`--check` 是给人（和真需要时的手动 CI 步骤）用的棘轮，不是每次提交的闸门。
